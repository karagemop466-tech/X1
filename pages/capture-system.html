The capture system: every official read, kept

The site used to publish one capture per dataset because the collector wrote data/pipeline/<dataset>.json and overwrote it on the next run — and because the collector's own commit step never actually pushed (see the box below). This page is the layer that fixes both: a dated, hash-addressed index of every read, with the drift pins that decide whether a read is publishable at all.

What was broken, in its own log. _ci/commit.log on main ends every scheduled run with MARKER: PUSH FAILED after 5 attempts. The commit step ran rm -rf _ci and git reset --mixed; _ci/*.log are tracked files (the comment beside the line claimed they were untracked), so two unstaged deletions were left in the tree, and git rebase refuses to run on a dirty tree. Every dataset the collector read was committed locally and thrown away, while the diagnostics log was pushed by the API — which is exactly the shape of main’s last commit before this page existed. The job now restores those files, rebases with --autostash, pushes captures and derived artefacts as one unit, and fails loudly if it cannot land what it collected. the log ↗ · the workflow ↗

Gate versus alarm, and why the split is written down. A violation whose kind is in fail_the_build stops a data publish (a missing field, a row count outside the pin, a duplicate key, a standings or slate that does not close). A violation in alarm_only is published next to the number that caused it. Both lists, and the reason for each placement, live in data/captures/config.json; the mutation test python3 scripts/pipeline/verify_captures.py --self-test proves all five pin classes can fail (5/5 caught on 2026-11-16).
