One row per requirement: the gate, and the number that clears it

This is the page the owner asked for in the brief — "Put a decision-readiness table on the landing page: one row per requirement, with the gate that blocks it and the number that would clear it." 53 requirements. 32 carry a current value computed at build time from a file in this repository or a dated capture; the other 21 are left blank with the reason written out, because a number that was not measured is not a number.

53requirements in the registerevery one from the owner brief
14distinct gates namedfrom the two gate registers
32rows with a computed valuenot asserted, computed
7rows where the measurement contradicts the status textpublished, not hidden
How to read a row. The gate is the rule from data/gates.json (G0–G8, the strategy gauntlet) or data/pipeline/gates.json (G-01…G-14, the pipeline gates). The number that would clear it is the threshold written into that gate. The current value is recomputed by tools/build_decision_readiness.py every time the site is built, so it cannot drift out of date without the build saying so. Where the register's own status sentence disagrees with the measurement, both are printed. Nothing here is rounded up.

What this page cannot tell you

  • It cannot price anything. No row here is a price. The only price-shaped numbers on the site come from a third-party mirror, and every row that uses one says so.
  • It cannot confirm a starter. The league publishes no depth chart; the depth rows are club self-reports, and the clubs that print "unofficial" on their own charts are named on the Flagged page.
  • It cannot settle a result that has not finished. The Week 10 injury table was re-captured on 2026-11-15 and 16 rows differ from the 2026-11-14 capture. Which capture is "right" depends on the moment it was read; the timestamp on each row is what makes that answerable, and it is present on the capture, not on the published table.
